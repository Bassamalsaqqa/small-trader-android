## Production composition

- `smalltrader.offlineOwnerPilot` defaults to false. The preparation UI also requires explicit positive `smalltrader.offlineCatalogMaxPages` and `smalltrader.offlineCatalogMaxProducts` build properties; neither has a numeric fallback. All economic limits, currency precision, tax, warehouse, cash account and customer routing come from an explicitly acquired server lease.
- The authenticated pilot UI observes validated Android network connectivity, prepares all catalog pages, acquires the lease, saves an authenticated restricted bootstrap subset and exposes explicit synchronization. The transport now permits the bounded product `catalog_snapshot_version` query parameter needed for subsequent pages.
- After restart, the restricted workspace can be entered from a network-error or sign-in screen. It does not create `ReadReady`, a bearer, an online scope or current permissions. Its private repository is inaccessible to the UI except through catalog, provisional cash capture and pending/recovery operations; its transport and bearer provider reject network access. Reconnection returns to normal server bootstrap validation. Replay still requires the existing live authenticated gateway and revocation checks.
- The restricted bootstrap uses AtomicFile and the production AES-GCM/Android Keystore engine. Its authenticated payload binds the prior secure session digest and actor/company/device/lease, historical display labels and leased routing. Reading requires the same persisted authenticated session, verified boot, unexpired lease, complete catalog, matching installation and unlocked queue. Logout, login/scope changes and accepted authorization denial invalidate the cache. Missing/corrupt keys/cache fail closed and never remove economic intents.
- The restricted screen exposes sale capture, pending count, held-cash review identifiers, reconnect and logout only. It labels its restricted status in English and Arabic, keeps numeric amounts isolated, supports editable exact quantity/price and uses an immutable client event UUID across capture retries. It cannot synchronize or claim current authentication offline.

## Durable authority and immutable history

- Android API 24+ `Settings.Global.BOOT_COUNT` supplies boot continuity. Unknown continuity and reboot fail closed. The encrypted envelope retains the first server-issued time/elapsed-realtime anchor; wall time cannot extend it. Both expiry and maximum offline hours apply. A reboot requires a new server lease ID; an old issuance timestamp is never attached to a fresh monotonic anchor.
- An independently encrypted per-lease baseline survives catalog replacement and active-lease removal. Same-lease acquisition retains the original budget and anchor. Confirmed/rejected local cash remains consumed.
- Acquisition reconciles server counters against the original baseline plus locally confirmed immutable events in the same SQLite transaction as local lease persistence. An unknown acknowledgement or inconsistent counters fails acquisition and rolls back local replacement; canonical acknowledgements must first be recovered online. No local confirmation is fabricated from counters alone.
- Production outbox composition requires durable current lease authority and active scope before/after capture, including retries. The boundary validates the actual event's leased currency, routing (including walk-in customer), catalog unit/conversion provenance, tax profile, calculated line amounts and capture window. Direct `captureSaleV2` cannot admit offline events through that production instance. Retries retain the original durable timestamp/receipt and compare all remaining canonical payload fields. The storage-only constructor behavior remains available for existing low-level storage tests; it is not an offline authorization claim.
- Catalog pages/completeness remain encrypted and atomic. Page versions, final-page state, scope, duplicate product IDs, byte bounds and authenticated blobs fail closed. Failed preparation preserves the prior snapshot. Capture verifies product-unit/conversion provenance against the durable leased catalog, independently of concurrent browsing state.
- Human tender inputs retain the two-decimal entry policy. Calculated settlement/change use the authoritative currency precision, preserving exact JOD fractional economics without rounding economic storage. Online capture behavior is unchanged.

## Queue reads

Queue revision metadata updates transactionally through scoped SQLite triggers. Reads use the existing scoped indexes and keyset pages of at most 100 outstanding offline events, excluding confirmed history before decryption. Unchanged refreshes reuse the scoped records and exact aggregate; a mutation rebuilds the outstanding subset. No plaintext financial aggregate is persisted. Cold/revised reads remain proportional to outstanding records, rather than confirmed history. The focused test counts decryptions across repeated refresh, another scope and confirmation invalidation.
